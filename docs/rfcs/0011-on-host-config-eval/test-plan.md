# Test plan — structural contracts and behavioral gates

The implementation changes evaluation, rendering, storage provisioning, and
boot activation while preserving strict system invariants. Tests therefore pin
the contracts and observable behavior directly; they do not commit generated
system images, unit trees, activation scripts, package versions, or normalized
store paths as source fixtures.

Nix output interpolation remains the source of truth. `${drv}` carries string
context and resolves to the realized output, while `builtins.placeholder "out"`
handles a derivation's self-reference. Focused checks verify that context and
the resulting structure without duplicating generated bytes.

## Contract checks

- `checks.system-structure` evaluates every discovered variant, requires the
  core rendered outputs to retain Nix context, realizes the systemd unit tree,
  and compares its path inventory with the pure configuration manifest.
- `checks.config-manifest` validates the complete shared manifest schema,
  ownership coverage, input identities, and pure-data boundary.
- `checks.systemd-lib` and `checks.systemd-generate` cover unit rendering,
  placeholder substitution, job-script identity, install links, and materialized
  unit contents with small purpose-built fixtures.
- `checks.config-materialize` and `checks.config-parity` cover deterministic
  materialization and equality across the supported rendering paths.
- Rust unit/integration tests cover resolver failures, provenance, activation
  transaction ordering, generation retention, and image state transitions.

## Behavioral checks

Fleet tests assert externally visible outcomes across the full lifecycle:

- atomic `/etc` staging, swap, recovery, and daemon reconciliation;
- root-a/root-b/var/swap provisioning and later-boot idempotency;
- authenticated metadata, host evaluation, package resolution, and degraded
  operation;
- Secure Boot, dm-verity, TPM measurement, image staging, counted boot,
  blessing, fallback, retry, rollback, and garbage-collection retention.

Guest introspection follows the harness constraints (`lib/testing/vm.nix`,
`vm.succeed`/`vm.fail`/`vm.wait_for_unit`; no host tools are introduced into
guest assertions).

## New-subsystem tests (change set — authored red-first, per phase)

These have no current equivalent, so they go red→green as each phase lands. They
are *specified here* so the tests are written before the code:

- **On-host eval → manifest** (`fleet`): agent receives literal-Nix user-data →
  evaluates → emits manifest; **eval twice ⇒ byte-identical** (determinism gate);
  manifest has the expected `etc`/`units`/`jobScripts`/`inputs` shape.
- **Resolve↔eval fixpoint** (`checks.eval` + `fleet`): a host.nix enabling a
  package whose config module isn't present pulls the **config output first**,
  re-evals, converges; a missing provider fails legibly; a cycle dumps the trace.
- **`module_abi` gate** (`checks.eval`): a config module with an incompatible
  `module_abi_compat` is **refused pre-eval**, fail-closed, old gen stays live.
- **Two-axis generations** (`fleet`): config rollback is a pointer switch
  (no eval, no reboot); cross-ABI rollback **re-evals** retained inputs; `apm gc`
  does **not** break cross-ABI re-eval (the `cfgsrc/` root, review M-gc-inputs).
- **Unit graph / degraded boot** (`fleet`, from `apm-system-activation-fail`): a
  single failing package fetch ⇒ `is-system-running = degraded`, `multi-user`
  reached, healthy packages live, box SSH-reachable; the committed gen is the
  **re-projected** (subset) manifest, still content-addressed.
- **systemd-repart substrate** (`fleet`): explicit `systemctl status
  systemd-repart-*` + idempotency (carve+grow on fresh VM, **dry-run-only on
  reboot**) + the destructive-op state-probe guards run once.
- **`aos metadata` agent** (`checks` + `fleet`): per-platform fetch over recorded
  fixtures (offline channels first), exact host.nix/hash retention, platform-mode
  authorization, signed-mode initrd verification against public anchors,
  first-boot typed storage-plan validation/rendering, facts → `host.facts.*`,
  and the static-networking seed for DHCP-less clouds.
- **Provisioning commit matrix** (`Rust` + `checks.eval` + `fleet`): operator
  and no-input fallback arms; exact-byte signed acceptance/rejection; pending
  marker fail-closed recovery; committed coherent/divergent/unavailable
  dry-run outcomes; root-first multi-device rendering; grow-to-fill placement;
  durable audit/definition state; last-known-good runtime-input restoration;
  measured-boot raw `/var`; out-of-band disks carrying a baked committed
  marker; and a second boot proving full runtime evaluation repeats while
  partition sizes remain unchanged.
- **Conscription / capability-scoped contribution** (`checks.eval`): a foreign
  `enable` write is rejected at resolve time (its paths are not a subset of the
  installed owner's contributable surface in `SystemRoots`); a contribution to an
  owner-declared contributable sub-path is allowed; provenance from the
  authenticated source
  (forged `_file` does not earn operator priority — review M-forgeable-file).

## How a check is added

- **Pure-eval / global:** add `lib/testing/<name>.nix`, import in
  `default.nix`'s `checks` rec → `nix-build -A checks.<name>`.
- **Module VM check:** `modules/tests/<name>.nix` defining `system.checks.<name>`
  → auto-wrapped by `modules/base/checks.nix` → `nix-build -A
  systems.server.checks.<name>`.
- **Fleet:** `tests/fleet/<name>.nix` (machines + `testScript`) → auto-discovered
  → `nix-build -A checks.fleet.<name>`.
- **Rust:** `crates/aos-package/tests/<name>.rs` → `cargo test`.

## Sequencing

1. Land focused schema, structural, and parity tests with each interface.
2. Land each subsystem's negative and failure-path tests with its implementation.
3. Run the non-KVM aggregate, then the complete fleet aggregate on a Linux/KVM
   builder before merge.
