# Registry web surface

Every registry can serve its own static web pages from the same bucket or CDN
that serves its git and Nix-cache surfaces, with no Hub in the serving path.
The surface has two tiers: content-bearing no-JS pages generated by
`apr web generate`, and an optional client-side WASM application that
progressively enhances those pages in place. A Hub, when present, renders its
own browse pages from its index; this page covers only the registry-owned
static surface.

## Components

| Component | Location | Role |
|---|---|---|
| Generator | `crates/registry/aos-registry-authoring/src/registry/webgen.rs` | Turns the committed `registry.toml` and package TOMLs into HTML pages and JSON snapshots. |
| CLI | `apr web generate` (`crates/registry/aos-registry-authoring/src/commands.rs`) | Writes the surface to an output directory, optionally staging a built SPA dist. |
| SPA | `crates/registry/aos-registry-web` | Leptos client-side-rendered app compiled to `wasm32-unknown-unknown` with `trunk`. |
| Shared reader | `crates/registry/aos-registry-format` | The wasm-clean git object, tag, ref, and SSHSIG reader used by the SPA, the Hub indexer, and `apm`. |

The SPA is built separately from the native workspace (Rust to wasm through
`trunk build --release`) to avoid a build-graph cycle; `apr web generate
--spa-dist <dir>` then ships the built dist.

## Generated layout

The generator writes this tree under its output directory. Every file here is
mutable (none is hash-named), so it is uploaded with the low-TTL class of the
static-origin upload; see [`http-layout.md`](http-layout.md) §6.

```text
index.html                 registry home: packages table, channels, trust note
web/config.json            branding defaults (name, accent?, hub_url?)
web/index.json             registry metadata and package summary snapshot
web/packages/<name>.json   per-package versions x platforms snapshot
browse/<name>.html         per-package static page (no-JS)
```

With `--spa-dist`, the generator also copies the dist's hash-named artifacts
into `web/` under normalized names (`app-<hash>_bg.wasm`, `app-<hash>.js`,
`style-<hash>.css`) and injects a same-origin module loader and stylesheet link
into every generated page. `crates/registry/aos-registry-web/Trunk.toml` sets
`filehash = true` and `public_url = "/web/"` so trunk's output matches that
shape.

The JSON snapshots are data contracts the SPA reads. `web/index.json`:

```json
{
  "name": "aos-core",
  "description": "The core AOS registry",
  "generator": "apr web generate",
  "generated_at": "2026-06-13T00:00:00Z",
  "packages": [
    { "name": "curl", "latest_version": "8.5.0",
      "description": "URL transfers", "license": "MIT" }
  ]
}
```

`web/packages/<name>.json` lists each version's platforms with `store_path`,
`nar_hash`, `nar_size`, and `closure_size`. The snapshots are a distribution
listing only: they carry package and artifact coordinates, not a package
option or method schema. Schema-aware clients use the signed runtime document
served by `apm`, the Hub, or the language server.

## Asset and content policy

- Every page is first-party: inline CSS and no external stylesheet, script,
  font, or analytics URL.
- All dynamic text is HTML-escaped, so a hostile package description cannot
  inject markup.
- `web/config.json`'s optional `hub_url` is the only absolute off-origin URL,
  and it is data the SPA reads, never an asset reference baked into a page.
- The pages are complete without JavaScript; `curl` and `lynx` see real
  content.

## The SPA

When WASM runs, the SPA (`crates/registry/aos-registry-web/src/lib.rs`):

- fetches `web/config.json` and `web/index.json` same-origin (no CORS) and
  renders the registry home and per-package views from the generator's exact
  field shapes (`model`);
- runs the verification badge entirely in the browser (`verify`): it fetches
  the channel partition tag and the committed `keys.toml` roster same-origin
  and performs real Ed25519 verification of the partition, release tag, and
  commit chain with `aos-registry-format`, rendering a result such as
  `verified in your browser: partition -> 1.4.2 -> commit ab12...`;
- when `hub_url` is set, searches the Hub over Connect-JSON (`net`); otherwise
  it filters `index.json` client-side.

Because the badge reuses the same reader as the Hub indexer and `apm`, one
parser verifies registry surfaces on the server, in the Worker, and in the
browser. The trust model it checks is described in
[`signing-and-trust.md`](signing-and-trust.md).
