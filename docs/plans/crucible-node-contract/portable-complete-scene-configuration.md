# Portable complete-scene configuration

`crucible.complete-scene.configuration/1` is a logical preparation recipe for the
explicit operationally funded collecting route. It is separate from installation
editions `/7` and `/8` and from all saved coordinator, runtime and native formats.
The actor constructs one genuine local CodeHost and a new coordinator before
encoding any derived initial reference or launch, then retains that same owner.

The ordinary `serve-complete-scene` entry accepts the independently pinned input
through its existing manifest/expected-reference arguments. Configuration is
selected only when an explicit operational policy has installed the original
whole-parent reservation before the Runtime and actors. The default route and
public installation-only APIs do not infer this format or supply a fallback.
The original `CompleteScenePrepare` command triggers preparation after normal
startup and signal polling. The funded foundation continues to return the
existing Refused response; it does not advertise preparation success or Ready.

The closed root has the following fields. This example is a shape description;
selection, measurement, content and resource records are not abbreviated JSON
inputs accepted by the decoder.

```text
schema: "crucible.complete-scene.configuration/1"
mechanism: "SourceSignedImport18"
restoration: {complete_restore: "SourceSignedTransfer12",
              restore_input_emitter: "CanonicalSdkRestoreInputs12",
              fresh_restore_allocation: "completed_admit13"}
measurements: [Measurement; 3]
participants: [Participant; 3]
host: HostSchedulingSelection
world: WorldBinding
requirements: ScenarioRequirements
initial: {activation_id: Id, generation: U64,
          native_prepared_tokens: [Id; 3]}
content: [{reference: ContentRef, bytes: Bytes}, ...]
resources: ResourceLimits
maximum_initial_bytes: usize
maximum_native_rows: usize
maximum_operations: usize
maximum_retained_outputs: usize
maximum_coordinator_records: usize
write_watchdog_ms: u64
```

Nested records reuse the existing closed complete7 declaration types. Generation
must be nonzero; all IDs validate. The three native tokens are untrusted expected
correlation DATA, not evidence that a native participant prepared or received a
capability. The actual Source and receiver paths must still establish their
original typed bindings. The root contains no Host prepared token, coordinator,
initial-node snapshot, preparations, scheduler, receipt or hash-repair directive.
Missing or foreign fields refuse.

This is the existing fixed unqualified producer/relay/sink plus Host collecting
profile, not arbitrary deterministic-scenario configuration. CompleteFive requires
native exact-execution and preservation facets, Unqualified advertised native
guarantees and Nondeterministic effective native rows/world. The Host's initial
row comes unchanged from its genuine owner. Original graph admission requires the
exact four-node accepted-nondeterminism roster and refuses deterministic scenario
requirements. Differently advertised guarantees still refuse through the defining
coordinator and Source validators; this builder does not weaken or reclassify a
qualified node from another profile.

The four-node collecting recipe requires 1 through 64 operations and three
retained outputs. All other existing declaration, canonical pinned-file,
measurement and content limits remain in force. The new profile does not change
old installation policies, accepted snapshot bytes or runtime resource ceilings.

The builder derives native participant and initial-node rows from their typed
installations and independently verified content. It obtains the Host initial
node and token only from the newly constructed actual Host. Activation uses the
recipe ID/generation and the logical world/owner roster; clock and boundary start
at zero, the scheduler is uninitialized and preparations are empty. The unchanged
coordinator validator checks each participant, then original complete graph
admission, CodeHost currentness and same-allocation checks still apply.

The private materialized selection uses the existing complete7 compiled family;
it is not decoded or relabeled installation7 bytes. Prepared retains the actual
configuration path and independently pinned ContentRef as DATA provenance. Its
exhaustive observer counts their actual backing alongside the generated
coordinator and other originals. The already accepted whole-parent deployment
reservation covers parent operational work separately; its address-space ceiling
is never reported as measured storage or Source semantic credit.

Two processes can consume the same pinned recipe and logical world while deriving
different operational Host tokens, coordinator bytes and initial/launch refs.
This format does not promise cross-process equality of receipts, incarnations,
operational commitments or saved continuation bytes. Existing PID/thread/Rc,
Arm/preparation, restored-ticket and snapshot currentness rules remain unchanged.

After template authentication, the actor polls each actual confined worker
through its original job, accepts the sealed completion and separately admits
parent startup-bank copies. Successful construction transfers the retained
executable File, signing key and private identity into the original Source's
private Birth. Completion bytes and failed allocation prefixes remain owned.
The original launch and Source are authenticated before and after construction;
ordinary Sources and the legacy in-process path cannot enter this transition.

This stage supplies no Initial/Recipe, native startup, snapshot, capture,
preservation or Ready authority. The public preparation response remains Refused.
Preparation failures retain the funded capsule/credit and any actual namespace
obligation; shutdown closes receivers before original-descriptor cleanup. A
failed cleanup keeps the original owner and credit until it genuinely succeeds.
